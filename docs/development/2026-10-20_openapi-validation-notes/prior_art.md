# Prior art: silently-ignored REST filter parameters (NetBox / DRF / django-filter) and OpenAPI-driven validation of LLM tool calls

Scope note: survey as of 2026-10-20. "Measured locally" items were run on 2026-10-20 against the NetBox instance used by this project (NetBox 4.3.3-Docker, Django 5.2.3, no plugins, `http://localhost:8000`, read-only token) and against the netboxlabs/netbox-mcp-server checkout at `/home/ola/dev/rnd/mcp/testmcp/netbox-mcp-server` (upstream tag v1.0.0 plus three local, unpublished commits). Each finding is tagged **[implemented]**, **[proposed]**, **[measured]** or **[speculation]**.

## KQ1. Does NetBox, DRF or django-filter offer a server-side strict mode that rejects unknown filter parameters?

### Takeaway
No. Neither NetBox, Django REST Framework nor django-filter (26.2) has a setting that rejects *unknown* query parameters; unknown keys never reach the FilterSet form, so they are ignored by construction. django-filter's old `STRICTNESS`/`FILTERS_STRICTNESS` only ever governed *invalid values of known filters*, and it was removed in 2.0 in favour of the DRF backend's `raise_exception = True`. I found no NetBox issue, discussion or PR proposing a `STRICT_FILTERING`-style setting; the only NetBox-side activity is tightening 500s into 400s for malformed values of *known* filters (#23328 / #23333, Oct 2026).

### Cited Findings
- django-filter's DRF backend raises a 400 only when the bound form is invalid: `if not filterset.is_valid() and self.raise_exception: raise utils.translate_validation(filterset.errors)`; `raise_exception = True` is the class default. Nothing inspects unrecognised keys. **[implemented]** — [django_filters/rest_framework/backends.py](https://github.com/carltongibson/django-filter/blob/main/django_filters/rest_framework/backends.py)
- `FilterSet.filter_queryset` iterates only `self.form.cleaned_data.items()`, i.e. only declared filters; a query key that is not a form field cannot produce an error or a filter. **[implemented]** — [django_filters/filterset.py](https://github.com/carltongibson/django-filter/blob/main/django_filters/filterset.py)
- django-filter 1.x had `STRICTNESS.RETURN_NO_RESULTS` (default), `STRICTNESS.IGNORE` and `STRICTNESS.RAISE_VALIDATION_ERROR` ("generally useful with APIs"), set via `Meta.strict` or the `FILTERS_STRICTNESS` setting. All three concern filters that "fail to validate", not unknown names. **[historical]** — [django-filter 1.1.0 FilterSet options](https://django-filter.readthedocs.io/en/1.1.0/ref/filterset.html)
- django-filter 2.0 migration guide: "Strictness handling has been removed from the `FilterSet` and added to the view layer", removing `FILTERS_STRICTNESS`, `Meta.strict` and the `strict` initializer argument; "To alter strictness behavior, the appropriate view code should be overridden." **[implemented]** — [Migration Guide](https://django-filter.readthedocs.io/en/stable/guide/migration.html)
- A 2017 maintainer issue "Change strictness default to RAISE_VALIDATION_ERROR for DRF?" (closed next day) is the origin of the DRF backend's raise-on-invalid default. — [carltongibson/django-filter#650](https://github.com/carltongibson/django-filter/issues/650)
- DRF's settings reference has no option for rejecting unknown query parameters or any "strict" mode; `NON_FIELD_ERRORS_KEY` is only "the key that should be used for serializer errors that do not refer to a specific field" (default `non_field_errors`). There is no `?strict=` query parameter in DRF. **[implemented / absent]** — [DRF settings](https://www.django-rest-framework.org/api-guide/settings/)
- NetBox's `BaseFilterSet` generates lookup variants at class-creation time (`new_filter_name = f'{existing_filter_name}__{lookup_name}'` from `FILTER_NUMERIC_BASED_LOOKUP_MAP`, `FILTER_CHAR_BASED_LOOKUP_MAP`, `FILTER_NEGATION_LOOKUP_MAP`, `FILTER_TAG_LOOKUP_MAP`, `FILTER_TREENODE_NEGATION_LOOKUP_MAP`, `FILTER_ARRAY_BASED_LOOKUP_MAP`), and `NetBoxModelFilterSet.__init__` adds `cf_<name>` filters per instance from `CustomField.objects.get_for_model(...)`. The code "doesn't explicitly reject unknown parameters ... silently ignoring unmatched keys." **[implemented]** — [netbox/netbox/filtersets.py](https://github.com/netbox-community/netbox/blob/main/netbox/netbox/filtersets.py)
- NetBox's REST filtering reference documents lookups (`n, lt, lte, gt, gte, empty` for numeric; `n, ic, nic, isw, nisw, iew, niew, ie, nie, empty, regex, iregex` for strings; `n` only for FKs; `n`/`any` for tags), multi-value OR via repeated params, and `cf_` custom-field filters. It says nothing about unknown parameters being rejected or ignored. There is no `in` lookup in the documented list. **[implemented]** — [docs/reference/filtering.md](https://github.com/netbox-community/netbox/blob/main/docs/reference/filtering.md)
- GitHub issue search of `netbox-community/netbox` for "unknown filter parameter", "ignore unknown query parameters", "strict filter api", "filterset unknown field 400", "undefined query parameter api" (run 2026-10-20 via the GitHub search API) returned no issue, discussion or PR proposing rejection of unknown filter parameters. The nearest hits are #23328/#23333 (malformed *values*) and #23397 (performance of FilterSet construction). **[absent]** — [GitHub search API](https://api.github.com/search/issues?q=repo:netbox-community/netbox+unknown+filter+parameter)
- NetBox #23397 (open, 2026-10-14, "type: performance") proposes a `NetBoxFilterBackend` that skips FilterSet construction when "every supplied parameter is a known non-filter control (`brief`, `export`, `fields`, `format`, `limit`, `offset`, `omit`, `ordering`, or `start`)", while keeping "the existing path for actual or unknown filter parameters". It reports `DeviceFilterSet` has 362 filters and ~28 ms setup overhead. This is the closest NetBox has come to enumerating "known control params vs. filter params" server-side, and it explicitly preserves the ignore-unknown behaviour. **[proposed]** — [netbox#23397](https://github.com/netbox-community/netbox/issues/23397)
- Measured locally on NetBox 4.3.3: `GET /api/dcim/devices/?bogus_param=1&limit=1` → HTTP 200, `count: 141` (identical to the unfiltered count); `?site_id__in=1,2` → 200, `count: 141`; `?ordering=bogus` → 200, unordered results, the bogus `ordering` echoed in the `next` link. **[measured]**

### Inferences
- Any strictness must live client-side or in a NetBox plugin/custom filter backend; nothing upstream is planned. A plugin could subclass `DjangoFilterBackend` (as #23397 sketches) and compare `request.query_params` to `filterset.filters` + control params, but that would be a third-party change, not a NetBox setting.
- Because lookups are generated at class-creation time and custom fields at instance time, a server-side strict check would need the instantiated FilterSet (not `base_filters`) to avoid rejecting `cf_*`.

### Gaps
- I did not find any NetBox *Discussion* (as opposed to issue) threads on this topic; the GitHub search API used covers issues and PRs only.
- No NetBox plugin implementing "reject unknown filters" was found by search.

## KQ2. When does NetBox's REST API return 400 for a query parameter instead of ignoring it?

### Takeaway
A 400 is produced only when a *known* filter's form field fails validation (wrong type, invalid choice, out-of-range), via django-filter's `raise_exception`. Unknown names, unknown lookup suffixes (`__in`), unknown `ordering` values and unknown `cf_` names are all ignored with 200. As of NetBox 4.7.x, #23333 converts several remaining 500s on malformed values into 400s (or empty results).

### Cited Findings
- Measured locally (NetBox 4.3.3): `?status=bogus` → 400 `{"status": ["Select a valid choice. bogus is not one of the available choices."]}`; `?site_id=abc` → 400 `{"site_id": ["“abc” is not a valid value."]}`; `?bogus_param=1`, `?site_id__in=1,2`, `?ordering=bogus` → 200 with the full unfiltered count. **[measured]**
- NetBox #23328 (2026-10-07, bug, accepted, fixed 2026-10-12 for 4.7.x): `vlan_id`, `vlan`, `wwn`, `time_zone`, `unit`, `start_address`, `end_address` returned HTTP 500 on malformed values; expected "Either HTTP 400 naming the field, as `?unit=no-such-value` already returns (`{"unit": ["Enter a number."]}`), or an empty result, as `?address=no-such-value` on IP addresses has returned since #11470." — [netbox#23328](https://github.com/netbox-community/netbox/issues/23328)
- PR #23333 "Return empty results or a 400 for malformed filter values": "Each filter now returns a 400 naming the field, except the IP range address filters. Those discard invalid values and return an empty result". It adds an `InvalidValueFilterMixin` and notes "In the OpenAPI schema, `vlan_id` and `vlan` change from string to number". **[implemented, merged 2026-10-12]** — [netbox PR #23333](https://github.com/netbox-community/netbox/pull/23333)
- The documented way to discover valid choices is an authenticated `OPTIONS` request (`.actions.POST.status.choices`), which "works only if the API token used ... has permission to make a `POST` request". — [docs/reference/filtering.md](https://github.com/netbox-community/netbox/blob/main/docs/reference/filtering.md)
- Live verification table in this project (2026-10-06, NetBox 4.3.3): `device_id__in`, `id__in`, `site_id__in`, `name__in`, `vid__in` all returned the full table with 200; the bare-key list form (`{"device_id": [149,150]}` → repeated query params) filtered correctly. "No field class honours `__in` ... Unknown query parameters are ignored by DRF, hence no 400." **[measured, local doc]** — [2026-10-06_in-lookup-silently-ignored.md](/home/ola/dev/netboxdev/ollamaDeepAgents/docs/development/2026-10-06_in-lookup-silently-ignored.md)
- The changelog `action` filter takes `create`/`update`/`delete`; `created`/`updated`/`deleted` return HTTP 400 (verified live on NetBox 4.3.3, 2026-10-19). **[measured, local patch]** — [2026-10-19_netbox-mcp-server-changelog-action.patch](/home/ola/dev/netboxdev/ollamaDeepAgents/docs/development/2026-10-19_netbox-mcp-server-changelog-action.patch)
- NetBox #21529 (fixed v4.5.8): PATCHing `custom_fields` with a non-existent field name was accepted and shown in the changelog — the write path also tolerated unknown custom-field keys until 4.5.8. — [netbox#21529](https://github.com/netbox-community/netbox/issues/21529)
- NetBox #20839 (fixed 4.4.x): two UI filter forms submitted `object_type=` where the filterset expected `object_type_id=`, "so the filterset ignores the value and the list doesn't change" — NetBox's own UI has been bitten by the same ignore-unknown behaviour. — [netbox#20839](https://github.com/netbox-community/netbox/issues/20839)

### Inferences
- The 400/ignore boundary is exactly "is this key a filter on the instantiated FilterSet". A client that knows the instantiated filter list can reproduce the boundary; a client that knows only the OpenAPI list can approximate it (see KQ8 for the gaps).
- Value validation strictness has been *increasing* in 2026 (#23333), but only for known filters; name strictness has not moved.

### Gaps
- I did not test NetBox 4.7.x live; the 4.3.3 measurements may differ in value handling for the fields touched by #23333 (names are unaffected).

## KQ3. NetBoxLabs netbox-mcp-server: how `validate_filters` works, and what has been filed about `__in`, `action=created` and search defaults

### Takeaway
Upstream `validate_filters` (v1.2.x) is a suffix allow-list plus a multi-hop (`a__b__c`) block; it knows nothing about field names, so unknown field names still pass through to NetBox and return the full table. The `__in` problem was filed as #79 (2026-03-12) and fixed by PR #144 in v1.2.0 (2026-05-26). I found no upstream issue or PR for `action=created` or for the search default-type gap; both exist only as local patches in this project. No upstream PR adds OpenAPI/schema-driven validation, and the upstream code has no near-miss suggestions.

### Cited Findings
- Upstream `validate_filters` (main, 2026-10): docstring "NetBox API does not support: `__in` suffix (pass a list as the field value instead ...), nested relationship queries like device__site_id"; `valid_suffixes = {n, ic, nic, isw, nisw, iew, niew, ie, nie, empty, regex, iregex, lt, lte, gt, gte}`; skips `limit, offset, fields, q`; keys without `__` are accepted unconditionally; `x__in` raises `ValueError("... '__in' lookup suffix is not supported and may be silently ignored by NetBox. Pass a list to the field directly instead: {'x': [1, 2, 3]}")`; anything else with ≥2 parts raises the multi-hop error. **[implemented]** — [src/netbox_mcp_server/server.py](https://github.com/netboxlabs/netbox-mcp-server/blob/main/src/netbox_mcp_server/server.py)
- `grep` of upstream `server.py` for `difflib`, `get_close_matches`, `openapi`, `schema`, `near` returns nothing: there is no field-name validation and no suggestion mechanism. Valid-type suggestions exist only for `object_type` (`valid_types = "\n".join(...)` in `netbox_search_objects`). **[measured, source inspection 2026-10-20]** — same file.
- Issue #79 "Tool description misleads LLMs about __in filter support — silently returns all records" (2026-03-12, Claude Code / claude-opus-4-6): `{"vminterface_id__in": [621493, 631527]}` "return >1k results — effectively every IP address in NetBox. The filter is silently ignored by NetBox/Django REST Framework (no error returned), so the LLM has no way to detect the failure". Suggested fix included "the MCP server could detect suspiciously large result sets when restrictive filters were provided." — [netbox-mcp-server#79](https://github.com/netboxlabs/netbox-mcp-server/issues/79)
- PR #144 "fix: reject __in lookups, suggest list-as-value form" (merged 2026-05-26, closes #79, supersedes #145 by llamafilm; "prepared with AI assistance") — shipped in v1.2.0 (2026-05-26). **[implemented]** — [PR #144](https://github.com/netboxlabs/netbox-mcp-server/pull/144); [Releases](https://github.com/netboxlabs/netbox-mcp-server/releases)
- The local checkout is upstream v1.0.0 (2025-10-31) plus three local commits: `796b065 fix: drop the in lookup suffix` (independent of #144, dated 2026-10-06), `d05d3f4 fix: change-log action values are create/update/delete`, `d7809d9 feat: search tenants, providers and manufacturers by default`. The latter two are saved as patches dated 2026-10-19 and are **not** filed upstream. **[measured, `git log`]** — [local repo](/home/ola/dev/rnd/mcp/testmcp/netbox-mcp-server); [patches](/home/ola/dev/netboxdev/ollamaDeepAgents/docs/development/)
- Upstream `netbox_get_changelogs` docstring still says "action: Filter by action type (created, updated, deleted)" while its example uses `{"action": "delete", ...}` — i.e. the upstream description is still wrong as of main (2026-10-08). No issue filed. **[implemented / bug]** — [server.py](https://github.com/netboxlabs/netbox-mcp-server/blob/main/src/netbox_mcp_server/server.py)
- Full upstream issue list (11 issues, all states, 2026-10-20) contains nothing about `action`, search defaults, unknown filter names, or OpenAPI validation: #186 stateless HTTP, #179 available-prefixes tool, #177 comparison listing, #175 elicitation-gated writes, #170 per-request token, #152 unauthenticated HTTP, #136 custom headers, #131, #130 PyPI, #119 custom objects, #88 dependency dashboard. **[absent]** — [issues](https://github.com/netboxlabs/netbox-mcp-server/issues?q=is%3Aissue)
- Tool-schema strictness history: PR #61 (merged 2026-04-20) changed parameter types to strings for n8n; reverted by #121; #120/#123 restored "strict JSON Schema types (`integer`/`array`/`object`)" and added `--n8n-compat`; `filters` is typed `{object, null}` in strict mode and `{string}` in compat mode. So `filters` remains a free-form dict at the MCP boundary. **[implemented]** — [PR #123](https://github.com/netboxlabs/netbox-mcp-server/pull/123); [PR #120](https://github.com/netboxlabs/netbox-mcp-server/pull/120)
- Open dependency PRs #180/#182 migrate to FastMCP 4 and httpx 2; current pin on main is `fastmcp>=3.2.0,<4` (PR #107). **[proposed]** — [PR #180](https://github.com/netboxlabs/netbox-mcp-server/pull/180)

### Inferences
- Upstream's design keeps `filters: dict` free-form and validates shape only; adding field-name validation would require either a hand-maintained per-type list, the OpenAPI spec, or an `OPTIONS` probe. None of the 188 PRs attempt this.
- The three local patches (action values, search defaults, `__in`) are candidate upstream contributions; only `__in` has an upstream equivalent (#144), and the local fix predates awareness of it.

### Gaps
- Could not read PR review comments (unauthenticated API budget); whether maintainers discussed schema-driven validation in #144/#145 review threads is unknown.

## KQ4. How other NetBox clients and community MCP servers validate filters

### Takeaway
pynetbox is the only NetBox client found with schema-driven filter validation: `strict_filters=True` (v7.6.0+, Jan 2026) checks `.filter()`/`.get()` kwargs against the parameter names of the instance's OpenAPI document, raising `ParameterValidationError`, with `cf_*` skipped (fixed 7.8.0). It offers no near-miss suggestions and fetches/caches the whole spec once per `Api` object. Among six NetBox MCP servers compared by ToolMesh (Aug 2026), only netboxlabs' and mhajder's document any filter validation, and both are pattern-based, not schema-based.

### Cited Findings
- pynetbox README: "NetBox doesn't validate filters passed to the GET API endpoints ... If a filter is incorrect, NetBox silently returns the entire database table content. Pynetbox allows to check provided parameters against NetBox OpenAPI specification before doing the call, and raise an exception if a parameter is incorrect." Enabled via `pynetbox.api(url, strict_filters=True)` or per call `filter(..., strict_filters=True)`. **[implemented]** — [pynetbox README](https://github.com/netbox-community/pynetbox/blob/master/README.md)
- Implementation (`Endpoint._validate_openapi_parameters`): looks up `self.api.openapi()["paths"]["/api/{app}/{endpoint}/"]["get"]["parameters"]`, builds `allowed_parameters = [p["name"] ...]`, skips keys starting with `cf_` ("per-instance dynamic and not listed in the OpenAPI spec"), and raises `ParameterValidationError([... "'{p}' is not allowed as parameter on path '...'" ...])`. Only `get` is supported "as for other methods NetBox already does proper validation". No type/enum checks, no suggestions. **[implemented]** — [pynetbox/core/endpoint.py](https://github.com/netbox-community/pynetbox/blob/master/pynetbox/core/endpoint.py)
- Spec fetch: `Api.openapi()` caches in `self._openapi`; `Request.get_openapi()` GETs `{base}/schema/` for NetBox ≥3.5 (else `docs/?format=openapi`). **[implemented]** — [pynetbox/core/api.py](https://github.com/netbox-community/pynetbox/blob/master/pynetbox/core/api.py); [pynetbox/core/query.py](https://github.com/netbox-community/pynetbox/blob/master/pynetbox/core/query.py)
- Origin: issue #695 "Filter arguments validation" (2025-06-02, m0nkeyc0de: "using the openapi description provided by NetBox itself, which is supposed to contain all the supported filter expressions"), PR #697 merged 2025-06-23. `strict_filters` is absent from the v7.5.0 tag and present in v7.6.0 (released 2026-01-09), so first release is 7.6.0. — [issue #695](https://github.com/netbox-community/pynetbox/issues/695); [PR #697](https://github.com/netbox-community/pynetbox/pull/697); [tags](https://github.com/netbox-community/pynetbox/tags)
- Issue #701 "strict_filter mechanism does not respect custom fields in filter" (2025-07-12; `cf_CRM_ID` rejected) fixed by PR #770 in v7.8.0 (2026-06-18) by skipping `cf_` keys. — [issue #701](https://github.com/netbox-community/pynetbox/issues/701); [PR #770](https://github.com/netbox-community/pynetbox/pull/770)
- pynetbox docs (NetBox Labs): "Custom field filters (`cf_<fieldname>` and their lookup suffixes such as `cf_<fieldname>__gt`) are dynamic and not listed in the OpenAPI specification. They are skipped by the validator". — [pynetbox advanced usage](https://netboxlabs.com/docs/sdks/pynetbox/advanced/)
- Latest pynetbox is 7.9.0 (2026-10-08, NetBox 4.7 support, Python ≥3.12). — [PyPI](https://pypi.org/project/pynetbox/)
- ToolMesh comparison (Aug 2026) lists nbox (13 tools), NetBox Labs Platform MCP Server ("nearly 100 tools"), NetBox MCP Enhanced/skuldgerry (~60), netboxlabs/netbox-mcp-server (4), netbox-mcp-rw (9, "input validation, tests and async support as open"), ToolMesh+netbox.dadl (608 tools). Only netboxlabs' entry mentions "filter validation that rejects `__in` and multi-hop lookups". — [toolmesh.io NetBox MCP comparison](https://www.toolmesh.io/en/mcp/netbox/)
- mhajder/netbox-mcp (139 core object types for NetBox 4.7, ~18-20 tools, GraphQL, allocation, branching): advertises "Filter validation that rejects filters NetBox would silently ignore (`__in`, multi-hop lookups)" — the same pattern-based approach; no OpenAPI-driven name check documented. — [mhajder/netbox-mcp](https://github.com/mhajder/netbox-mcp)
- No evidence was found that nbcli or netbox-python validate filter names (no search hits). **[absent]**

### Inferences
- pynetbox's approach (name-set membership from the live `/api/schema/`) is directly transferable to an MCP server and costs one 9 MB download per process. Its two known blind spots (custom fields, and anything else absent from the schema such as `__in`) are the same ones an MCP implementation would inherit.
- A local `difflib.get_close_matches` over the per-endpoint name set is a cheap addition pynetbox lacks (measured 2.4 ms for 292 names; see KQ5).

### Gaps
- No usage/adoption data on `strict_filters`; no reports of its false positives beyond #701.

## KQ5. Libraries for validating a request against an OpenAPI spec at runtime, and what they do with undeclared query parameters

### Takeaway
openapi-core (0.23.1, Python ≥3.10 <4) validates declared query parameters only; it iterates the spec's parameter list and never looks at extra keys, so `bogus_param`, `site_id__in` and `cf_foo` all pass. On the 9.3 MB NetBox spec its default constructor costs ~22 s (spec validation), 0 s with `spec_validator_cls=None`, and ~75 ms per request thereafter. openapi-spec-validator validates documents, not requests. Schemathesis is a test generator with per-parameter `validate()` helpers but no documented "reject unknown query parameter" mode. The only validator found with an explicit unknown-query-parameter switch is express-openapi-validator (Node, `allowUnknownQueryParameters`, default false). None offer near-miss suggestions; a 1.6 ms name-set index plus `difflib` does.

### Cited Findings
- openapi-core `_get_parameters` iterates `chainiters(operation_params, path_params)` (the spec's declared parameters), reads each from the request, and raises only `MissingRequiredParameter`/`ParameterValidationError` for *declared* params; undeclared request keys are never visited. **[implemented]** — [validation/request/validators.py](https://github.com/python-openapi/openapi-core/blob/master/openapi_core/validation/request/validators.py)
- openapi-core config: `spec_validator_cls=None` "disabling the validator can improve performance"; `additional_properties_default_policy="forbid"` treats omitted `additionalProperties` as false — this applies to JSON-schema *objects* (bodies), not to the set of query parameters. **[implemented]** — [openapi-core configuration](https://python-openapi.org/openapi-core/docs/latest/configuration/)
- Measured locally (openapi-core 0.23.1, jsonschema-path 0.4.6, Python 3.12, NetBox 4.3.3 spec = 9,313,713 bytes, 292 paths, 1,144 operations): `json.load` 0.07 s; `OpenAPI.from_dict(spec)` 21.89 s; with `Config(spec_validator_cls=None)` 0.00 s (lazy); `unmarshal_request` on `/api/dcim/devices/` 73–108 ms per call, warm `validate_request` 76 ms each (it walks all 292 declared params per call). Results: `?site_id=25` → `{'site_id': [25], 'limit': 1}`; `?bogus_param=1`, `?site_id__in=1,2`, `?cf_foo=1` → no error, empty query; `?site_id=abc` → `ParameterValidationError: Query parameter error: site_id`; `?status=bogus` → **no error** because NetBox's schema declares `status` as `array of string` with only `x-spec-enum-id`, no `enum` list. Note: without an `Authorization` header every call short-circuits with `SecurityValidationError` (spec requires `tokenAuth`/`cookieAuth`), which silently hides parameter results in `unmarshal_request().errors`. **[measured]**
- Cheap alternative measured locally: building `{endpoint: {param names}}` for all 151 GET-list endpoints from the parsed spec takes 1.6 ms; `difflib.get_close_matches('site_id__in', names, n=3, cutoff=0.6)` → `['site_id__n', 'site_id', 'site__n']` in 2.4 ms; `'tenant_name'` → `['tenant__n', 'tenant', 'tenant_id']`; `'device_role'` → `['device_type', 'device_type_id', 'device_type__n']` (a false lead: the real filter is `role`/`role_id`); `'role_name'` → `['role__n', 'role_id__n', 'role_id']`. **[measured]**
- jsonschema-path (openapi-core's accessor layer) ships a resolved-path LRU cache "enabled by default (resolved_cache_maxsize=128)" and recommends building one accessor per document and reusing it. — [jsonschema-path on PyPI](https://pypi.org/project/jsonschema-path/)
- openapi-spec-validator 0.9.0 validates spec documents (used by openapi-core's `spec_validator_cls`); it is the 22 s cost above and is not a request validator. — [PyPI](https://pypi.org/project/openapi-spec-validator/)
- Schemathesis 4.32.1 ("Adaptive API testing for OpenAPI and GraphQL", Python ≥3.11): its Python API exposes per-operation `get_parameter(name, location)` and `validate()` on parameters, aimed at test generation/conformance; no documented mode for rejecting undeclared query parameters at runtime. — [Schemathesis Python API](https://schemathesis.readthedocs.io/en/stable/reference/python/); [PyPI](https://pypi.org/project/schemathesis/)
- express-openapi-validator (Node): `allowUnknownQueryParameters` "Determines whether to allow undefined query parameters to pass validation", default `false`. This is the reference behaviour the Python libraries lack. — [express-openapi-validator validateRequests](https://cdimascio.github.io/express-openapi-validator-documentation/usage-validate-requests/)
- pynetbox's validator (KQ4) is effectively a 20-line name-set check with no library dependency. — [endpoint.py](https://github.com/netbox-community/pynetbox/blob/master/pynetbox/core/endpoint.py)

### Inferences
- For this problem openapi-core adds cost (75 ms/call, 22 s or a disabled spec validator at startup) without adding the one check needed (unknown names); it does add type checks for declared params, which NetBox already performs server-side with a 400. A name-set index with `difflib` suggestions is both faster and more targeted. **[inference]**
- Enum validation from the NetBox schema is not possible for `status`-style filters because the generated schema carries `x-spec-enum-id` without values; choices must come from `OPTIONS` (needs POST permission) or a hand-maintained table. **[inference from measured schema]**

### Gaps
- openapi-core startup was measured on Python 3.12 only (the project also has a 3.13 venv); behaviour should be the same but was not re-run.
- I found no Python library offering "did you mean" for query parameter names.

## KQ6. MCP-from-OpenAPI generators: typed parameters vs. free dict, and the cost for NetBox

### Takeaway
FastMCP's `from_openapi` (and Speakeasy/Stainless generators) flatten every OpenAPI parameter into a typed property of the tool's input schema, so an undeclared name cannot be passed — the problem disappears by construction, but only for names the spec declares (not `cf_*`, not `__in`). The cost for NetBox is large: the device-list tool alone would carry 292 properties (~24 KB, ~6k tokens), and the 151 list endpoints sum to 11,537 parameters; the spec has 1,144 operations. Stainless's own answer to this scale is "dynamic tools" (three meta-tools) or a code-execution tool rather than one-tool-per-operation.

### Cited Findings
- FastMCP OpenAPI integration: "A request body becomes a flat set of tool arguments, which is the shape LLM tool-calling APIs fill in most reliably"; query parameters become tool arguments; "By default, FastMCP skips parameters whose value is `None`"; name collisions get a location suffix ("a query parameter named `values` become `values` and `values__query`"); route maps (`RouteMap`, `MCPType.EXCLUDE`, tags) select which operations become tools. **[implemented, FastMCP ≥2.0; current PyPI 4.1.1]** — [gofastmcp.com/integrations/openapi](https://gofastmcp.com/integrations/openapi); [PyPI fastmcp](https://pypi.org/project/fastmcp/)
- Known FastMCP from_openapi defects: whole-body arguments overwrite same-named HTTP parameters (PrefectHQ/fastmcp#5112); `$ref` into a component property resolves wrongly (#5739). In the TypeScript port: generated `{name}__{location}` aliases can collide with literal names and overwrite schemas (punkpeye/fastmcp#408, PR #409); form-style object query params lose properties (`filter=[object+Object]`, #413); form arrays ignore `explode: false` (#397). **[bugs]** — [#5112](https://github.com/PrefectHQ/fastmcp/issues/5112); [#5739](https://github.com/PrefectHQ/fastmcp/issues/5739); [punkpeye#408](https://github.com/punkpeye/fastmcp/issues/408); [#413](https://github.com/punkpeye/fastmcp/issues/413); [#397](https://github.com/punkpeye/fastmcp/issues/397)
- Measured locally from the NetBox 4.3.3 spec: `/api/dcim/devices/` GET has 292 parameters (lookup suffix counts: `n` 63, `empty` 23, `gt/gte/lt/lte` 18 each, `ic/nic/isw/nisw/iew/niew/ie/nie` 6 each; no `__in`; no `cf_`); serialising them as a JSON-schema `properties` object is 24,383 chars (~6,095 tokens at 4 chars/token; only 72 of 292 have descriptions). 151 GET-list endpoints carry 11,537 parameters in total; 1,144 operations overall. **[measured]**
- NetBox #23397 reports the instantiated `DeviceFilterSet` has 362 filters (vs. 292 in the schema): the 70-filter difference is runtime-added filters (custom fields, etc.) that a spec-generated tool could not expose. — [netbox#23397](https://github.com/netbox-community/netbox/issues/23397)
- Speakeasy generates MCP tools that wrap SDK methods "with proper type definitions" using "Zod schemas for validation", with scopes (`--scope read`) and `x-speakeasy-mcp` to pick operations; the post does not discuss unknown-argument handling or tool-count limits. — [Speakeasy: Generate MCP servers from OpenAPI](https://www.speakeasy.com/blog/generate-mcp-from-openapi)
- Stainless "dynamic tools": "Large APIs with many endpoints can be difficult for LLMs to work with effectively when all endpoints are exposed as individual tools"; `--tools=dynamic` exposes `list_api_endpoints`, `get_api_endpoint_schema`, `invoke_api_endpoint` so the LLM discovers endpoints "without requiring the entire API schema to be loaded into its context window at once". Stainless later added a code-execution tool plus docs-search tool as the preferred shape. — [Stainless MCP dynamic tools](https://www.stainless.com/changelog/mcp-dynamic-tools/); [Stainless MCP code execution tool](https://www.stainless.com/changelog/mcp-code-execution-tool)
- snaggle-ai/openapi-mcp-server's README describes a 3-step flow (identify the OpenAPI document, summarise, pick endpoints) and gives no detail on parameter typing or unknown-argument handling. — [snaggle-ai/openapi-mcp-server](https://github.com/snaggle-ai/openapi-mcp-server)
- netboxlabs' server deliberately uses four generic tools with `filters: dict` rather than generation ("Advanced features (GraphQL, dynamic model discovery, etc.) are deliberately out of scope"). — [README](https://github.com/netboxlabs/netbox-mcp-server/blob/main/README.md)

### Inferences
- Generating NetBox tools from the spec trades a silent-ignore problem for a context-size problem (≈6k tokens for one list tool; hundreds of tools) and still cannot express custom fields. A hybrid — keep the generic `filters: dict` tool, validate keys against the per-endpoint name set from the spec, and surface near-misses — captures most of the benefit at ~2 ms per call. **[inference]**
- Stainless's dynamic-tools pattern (`get_api_endpoint_schema` on demand) is the closest published precedent for "schema on request, not in every tool description". **[inference]**

### Gaps
- No published token measurements for a FastMCP-generated NetBox server were found; the ~6k-token figure is a local estimate using 4 chars/token.

## KQ7. How agent frameworks and the literature handle tool-argument validation ("did you mean", structured errors), and experience reports on silently-ignored parameters

### Takeaway
Framework-level validation (FastMCP/pydantic, MCP inputSchema) checks a call against the tool's declared JSON schema; with a free-form `filters` object it cannot see inside. The 2026 arXiv literature frames this as closed-world resolution (registry membership + signature check) and notes that most failed calls are schema-valid-but-wrong; none of the found papers implement near-miss name correction. Practitioner reports (pynetbox README, netbox-mcp-server #79, dev.to posts) all identify "200 with unfiltered data" as a silent failure the model cannot detect, and recommend boundary validation with structured, actionable errors.

### Cited Findings
- "Closed-World Resolution Against Tool Hallucination in LLM Agents" (Laxmipriya Ganesh Iyer, arXiv 2609.19425, 16 Sep 2026): proposes "a training-free, closed-world resolver (registry membership plus a signature check)" before execution; across ten hosted models measured 322 genuine hallucinations on single-registry surfaces (raw-JSON interfaces 34 vs. 3 calls), and 154 more when MCP servers are merged "due to structural collisions and shadowing"; releases the Hallucinated-Tools Benchmark. — [arXiv:2609.19425](https://arxiv.org/abs/2609.19425)
- "Getting the Parameters Right" (Guoyao Yu et al., arXiv 2608.03071, 4 Aug 2026): parameter filling, not tool selection, is the bottleneck; in cloud-networking domains "frontier models succeed on fewer than half of tool calls"; probe-guided training raises exact match from 19.7% to 59.6%. — [arXiv:2608.03071](https://arxiv.org/abs/2608.03071)
- "Try, Check and Retry" (Chen et al., arXiv 2603.11495, 12 Mar 2026): Try-Check-Retry with a rule-based consistency validator for long-context tool calling; up to +25.10% on BFCL/ACEBench. The search summary's claim that "only 2.1% of failed calls ... violate the schema" could not be located in the abstract and is **unverified**. — [arXiv:2603.11495](https://arxiv.org/abs/2603.11495)
- Related 2026 work: "ToolHACE: A Dataset for Detecting Hallucinations in Tool-Based LLM Responses" (arXiv 2610.17125) and "Internal Representations as Indicators of Hallucinations in Agent Tool Selection" (arXiv 2601.05214). Titles only; not read in full. — [2610.17125](https://arxiv.org/html/2610.17125v1); [2601.05214](https://arxiv.org/abs/2601.05214)
- Adamo Software, "Tool-use API design for LLMs: 5 patterns" (dev.to, 5 May 2025): self-describing results (`is_complete`, `next_action_hint`), distinguish failure types from empty results, hard call budgets, deduplication, and "Parameter Validation at Boundaries" using Pydantic "returning structured error responses with user-facing hints". — [dev.to](https://dev.to/adamo_software/tool-use-api-design-for-llms-5-patterns-that-prevent-agent-loops-and-silent-failures-f29)
- "Why LLM Agents Fail Silently and How to Debug Them" (dev.to, mudassirworks) defines a silent failure as an agent that "completes without raising an exception but produces a wrong or incomplete result"; "3 Patterns That Fix LLM API Calling" (docat0209, 2026) recommends generating tool definitions from the OpenAPI spec and validating parameters against the schema before the call. — [dev.to mudassirworks](https://dev.to/mudassirworks/why-llm-agents-fail-silently-and-how-to-debug-them-251l); [dev.to docat0209](https://dev.to/docat0209/3-patterns-that-fix-llm-api-calling-stop-getting-hallucinated-parameters-4n3b)
- Field report in this project (2026-10-06): a single `device_id__in` call returned 52,721 characters of other tenants' power outlets, the next model call took 283 s, and the agent answered 17 of 96 correctly after falling back to 12 per-device calls — "The cost was the failure, not the answer." The fix added an explicit `__in` branch to `suggest_alternative` and a `TOOL_VALIDATION_ERROR` before the call. **[measured, local]** — [2026-10-06 note](/home/ola/dev/netboxdev/ollamaDeepAgents/docs/development/2026-10-06_in-lookup-silently-ignored.md)
- netbox-mcp-server #79's reporter proposed a heuristic the server does not implement: "detect suspiciously large result sets when restrictive filters were provided". — [#79](https://github.com/netboxlabs/netbox-mcp-server/issues/79)
- netbox-mcp-server's MCP boundary validates `filters` only as `{object, null}` (FastMCP/pydantic), per `test_tool_registration.py` described in PR #120. — [PR #120](https://github.com/netboxlabs/netbox-mcp-server/pull/120)

### Inferences
- The literature's "signature check" is exactly what a free-form `filters` dict defeats; the practical move is to push the signature one level down (per-object-type parameter names) and return a structured error with candidates, which is what pynetbox (no candidates) and this project's local validator (`suggest_alternative`) already do in part. **[inference]**
- A result-size heuristic (#79) is complementary: it catches unknown keys the schema also lacks (e.g. `cf_` typos), at the cost of one extra unfiltered page. **[speculation]**

### Gaps
- No paper or framework docs found that implement "did you mean" over parameter names specifically; the 2.1% schema-violation statistic is unverified.
- Not checked: LangChain/langchain-mcp-adapters (installed: langchain-core 1.5.3, langchain-mcp-adapters 0.2.1, mcp 1.26.0) behaviour on tool-arg validation errors beyond passing through the server's error text.

## KQ8. Failure modes of OpenAPI-derived filter parameter lists for NetBox (drf-spectacular generation)

### Takeaway
NetBox's schema is generated by drf-spectacular's `DjangoFilterExtension` from `filterset_class.base_filters`, so it contains the class-time lookup variants (`__n`, `__ic`, ...) but not instance-time filters (custom fields `cf_*`, and anything a plugin adds at `__init__`), no `__in` (which NetBox does not support anyway), and no enum values for choice filters. It is ~9.3 MB, costs 22 s to spec-validate with openapi-core, and its parameter types shift between releases (#23333 changed `vlan_id`/`vlan` to number; #23428 documents IDs as int64).

### Cited Findings
- drf-spectacular's extension enumerates `for field_name, filter_field in filterset_class.base_filters.items():` — class-level filters only; method filters are typed from `get_type_hints(filter_method)['value']` with fallbacks to model-field inspection, choices, or string. **[implemented, drf-spectacular 0.30.0]** — [contrib/django_filters.py](https://github.com/tfranzel/drf-spectacular/blob/master/drf_spectacular/contrib/django_filters.py); [PyPI](https://pypi.org/project/drf-spectacular/)
- drf-spectacular #317 "Wrong django-filter types": filter fields can differ in type from the model field they target and the schema followed the model instead of the filter — a class of type errors inherited by consumers. — [drf-spectacular#317](https://github.com/tfranzel/drf-spectacular/issues/317)
- NetBox adds `cf_<name>` filters in `NetBoxModelFilterSet.__init__` (instance time), hence absent from `base_filters` and from the schema; pynetbox therefore whitelists any `cf_` prefix without checking the name. **[implemented]** — [filtersets.py](https://github.com/netbox-community/netbox/blob/main/netbox/netbox/filtersets.py); [pynetbox endpoint.py](https://github.com/netbox-community/pynetbox/blob/master/pynetbox/core/endpoint.py)
- Measured locally (NetBox 4.3.3 spec): device list has 292 params; `has cf_ params: False`; `has '__in' suffix: []`; `status` filter schema is `{"type":"array","items":{"type":"string","x-spec-enum-id":"8d8971779f16ee18"}}` with no `enum` list; `site_id` is `array of integer` (`style=form, explode=true`), so repeated params are the declared multi-value form. **[measured]**
- #23397: instantiated `DeviceFilterSet` has 362 filters vs 292 schema params (NetBox 4.7.3 vs 4.3.3 — different versions, so not an exact delta). — [netbox#23397](https://github.com/netbox-community/netbox/issues/23397)
- #23333 changed OpenAPI types for `vlan_id`/`vlan` from string to number; #23428 "Document object IDs as int64 in the OpenAPI schema" (merged 2026-10-18). Clients caching a spec across NetBox upgrades will see type drift. — [PR #23333](https://github.com/netbox-community/netbox/pull/23333); [PR #23428](https://github.com/netbox-community/netbox/pull/23428)
- Older schema-quality issues: #13370 "API - Description Document multiple issues" (2023), #12682 "Openapi schema is incomplete for /api/dcim/connected-device" (2023) — both closed. — [netbox#13370](https://github.com/netbox-community/netbox/issues/13370); [netbox#12682](https://github.com/netbox-community/netbox/issues/12682)
- Size/cost: `/api/schema/?format=json` = 9,313,713 bytes, served in 0.12 s locally; `json.load` 0.07 s; per-endpoint name-set index 1.6 ms; openapi-core spec validation 21.9 s. **[measured]**
- Plugin object types: netboxlabs' server auto-discovers plugin object types (README "Plugin Object Type Discovery"); plugin endpoints appear in the schema only if the plugin's viewsets are registered with the same drf-spectacular generator, and their filtersets are subject to the same `base_filters` limitation. **[implemented for discovery; the schema inclusion point is inference]** — [README](https://github.com/netboxlabs/netbox-mcp-server/blob/main/README.md)
- No GitHub issue about `/api/schema/` generation being slow or large was found in `netbox-community/netbox` (search "openapi schema generation slow" returned only #2665 from 2018). **[absent]**

### Inferences
- A schema-derived allow-list must (a) treat `cf_*` as pass-through (as pynetbox does) or augment it from `/api/extras/custom-fields/`, (b) be keyed by NetBox version/instance and refreshed on upgrade, and (c) not be used for choice validation. The 1.6 ms index makes per-request rebuilds unnecessary; a startup fetch plus on-demand refresh is enough. **[inference]**
- Because `__in` is absent from both the schema and NetBox's documented lookups, a schema-driven name check would have rejected `device_id__in` without any hand-written rule — the exact failure that cost 283 s in this project. **[inference from measured data]**

### Gaps
- Not measured: NetBox 4.7.x schema size and device-list parameter count (likely larger after #23333/#23428 and new 4.4–4.7 filters).
- Not verified: whether drf-spectacular `extend_schema_field` overrides in NetBox plugins affect parameter lists.
