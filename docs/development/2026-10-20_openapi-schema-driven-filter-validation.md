# Schema index catches names, hand rules keep values

Yes: the NetBox agent's filter validator should check filter keys against the per-endpoint parameter list of NetBox's own OpenAPI document, and enum values against the schema's enum tables, but it should do so as a layer in front of the hand-written rules, not as their replacement. Replayed over **1,237 recorded tool calls** from four v5 benchmark runs, a throwaway index built only from the 4.3.3 schema rejected **54 filter-key uses (27 distinct endpoint/key pairs) on 52 calls, every one verified live to be silently ignored by NetBox, with 0 false positives**; it also caught all **6 of 6** `action=created|updated|deleted` 400s through the enum table ([prototype_replay.md](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/prototype_replay.md)). Head to head, the schema check rejected **36 calls the hand-written validator let through** (almost all wrong relation names such as `devicerole_id`, `vlan_group_id`, `circuit_type_id`, `cable_id`, which returned whole tables and were accepted as answers), while the hand rules caught **3 calls the schema cannot see** (`tenant__n: null`, `vrf: "hvl-guest"`), so the two are complementary and together would have rejected **61 of 1,237 calls (4.9%)**. The cost is small: parsing the 9.3 MB schema takes **0.23 s**, the index is **3.65 MB resident (1.1 MB as JSON, 12 ms to reload)**, and a lookup is about **1 µs**. The investigation also surfaced a correctness bug that overrides the whole decision in importance: a JSON `null` filter value never reaches NetBox through the MCP client, so the **29 "correct" `<relation>_id: null` calls praised in the 2026-10-18 write-up were unfiltered queries**. On the GraphQL side, `graphql.validate` against the already-cached introspected schema reproduces NetBox's error messages **byte for byte in every category the pre-check tries to cover**, and exposes that `ordering` is wrongly whitelisted there. The recommendation is a four-layer REST validator (wire normalisation, schema key index, schema enum check, hand-written value rules and suggestions), a `validate`-based GraphQL pre-check with three retained hand rules, and an ordered plan whose first two steps are bug fixes that ship before any schema code.

Legend. **Measured** means a number produced in this investigation by replaying recorded calls or by a live GET against the local NetBox 4.3.3 instance; **inferred** means a conclusion drawn from measured facts; where a claim is a projection (what would happen on a future run) it is labelled as such.

## The hand-written validator misses the mistakes that matter most

The three days of ADR-0041, ADR-0043 and ADR-0044 fixed the forms that produced visible failures: `__in`, `__empty`/`__isnull` on relations, the ip-address containment keys, `action` values, GraphQL id lists ([ADR-0041](/home/ola/dev/netboxdev/rtf-research/docs/adr/0041-in-lookup-silently-ignored-reject-in-validator.md), [ADR-0043](/home/ola/dev/netboxdev/rtf-research/docs/adr/0043-filter-grammar-after-in-null-relations-ip-parent-graphql-ids.md)). The replay shows what that approach structurally cannot reach. The current `FilterValidator` reasons about lookup suffixes and a handful of named keys; it has no notion of which bare names exist on which endpoint. Of the 27 distinct unknown keys the schema index found, **thirteen are wrong names for a filter that exists** (`devicerole_id`, `device_role_id`, `device_role` for `role_id`/`role`; `circuit_type_id` and `cluster_type_id` for `type_id`; `vlan_group_id` for `group_id`; `cable_id` for `cable`; `assigned_object_id`/`assigned_object_type` for `object_id`/`object_type`; `contact_role_id` for `role_id`; `parent_prefix` for `parent`; `group_n` for `group__n`; `rack` for `rack_id`; `host_id` for `device_id`), three are filters that do not exist on that endpoint at all (`tenant_id` on virtual-disks and power-panels, `ip_address_id` on interfaces), and the remainder are the suffix and containment families the hand rules already address ([prototype_replay.md KQ1](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/prototype_replay.md)). Measured: those wrong-name keys account for **31 uses, 17 calls in the two latest runs alone**, and all of them recorded outcome `ok` with HTTP 200 and the full unfiltered population (141 devices, 94 VLANs, 381 cable terminations, 43 circuits). They were never retried, which is why the 2026-10-18 wasted-call analysis did not count them: they did not waste a call, they produced a wrong answer that the model accepted ([live_checks.json](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/live_checks.json)).

The underlying reason is mechanical and will not change upstream. django-filter's DRF backend raises a 400 only when a bound form field fails validation; `FilterSet.filter_queryset` iterates `self.form.cleaned_data`, so a query key that is not a declared filter can neither error nor filter ([django_filters/rest_framework/backends.py](https://github.com/carltongibson/django-filter/blob/main/django_filters/rest_framework/backends.py); [django_filters/filterset.py](https://github.com/carltongibson/django-filter/blob/main/django_filters/filterset.py)). The old `FILTERS_STRICTNESS` setting governed invalid values of known filters, never unknown names, and was removed in 2.0 ([Migration Guide](https://django-filter.readthedocs.io/en/stable/guide/migration.html)). A GitHub search of netbox-community/netbox for unknown-parameter strictness found no issue, discussion or PR; the only NetBox-side activity is converting 500s into 400s for malformed values of known filters (#23328/#23333) and a performance proposal, #23397, that explicitly preserves the ignore-unknown path ([netbox#23397](https://github.com/netbox-community/netbox/issues/23397); [netbox PR #23333](https://github.com/netbox-community/netbox/pull/23333)). Strictness therefore has to live on the client, and the question is only what authority the client consults.

The hand-written approach also drifts in both directions. The project's `VALID_SUFFIXES` lists `regex` and `iregex` as valid ([netbox_tools.py:28-33](/home/ola/dev/netboxdev/ollamaDeepAgents/src/tools/netbox_tools.py)), but measured live, `name__regex=^dmi01-akron` returns 141 of 141 devices: 4.3.3's `FILTER_CHAR_BASED_LOOKUP_MAP` has no `regex` entry, and the feature arrives in v4.3.5 via issue #19903 ([schema_coverage.md KQ1](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/schema_coverage.md); [netbox#19903](https://github.com/netbox-community/netbox/issues/19903)). On the GraphQL side `_LIST_FIELD_ARGS` whitelists `ordering`, yet measured against the introspected schema **115 of 117 `_list` fields take exactly `(filters, pagination)` and none takes `ordering`**; NetBox answers `Unknown argument 'ordering' on field 'Query.device_list'` ([graphql_introspection.md Q1, Q3](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/graphql_introspection.md)). A whitelist written from documentation of a version other than the one running is wrong on day one and stays wrong until someone notices; an index generated from the running instance's schema is right by construction for key names and becomes right again on upgrade.

## The schema is an exact authority for names and enums, a poor one for values

The question "is the OpenAPI document trustworthy?" has a precise answer because drf-spectacular's `DjangoFilterExtension` enumerates `filterset_class.base_filters`, the same class-level dictionary NetBox parses requests with ([drf-spectacular contrib/django_filters.py](https://github.com/tfranzel/drf-spectacular/blob/master/drf_spectacular/contrib/django_filters.py)). Measured over all 151 list-GET operations and 11,537 parameters, the schema reproduces NetBox's four lookup maps exactly: string fields get `n, ic, nic, ie, nie, isw, nisw, iew, niew, empty`; numeric and date-time fields get `n, lt, lte, gt, gte, empty`; FK, tree-node and tag filters get `n` only; booleans and method filters get nothing. **`__in` appears nowhere (0 of 11,537), `__isnull` and `__icontains` nowhere, `regex` nowhere, and no parameter has two `__` segments** ([schema_coverage.md KQ2](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/schema_coverage.md)). The 32 `*_id__empty` parameters are all char fields or generic-FK integer columns, never real FK filters, which is why `tenant__empty` and `tenant_id__empty` are absent from `/api/dcim/devices/` and why a key check catches them without a rule. Against the hand-found table of twenty silently-ignored forms, a pure key check catches fifteen; against the 27 keys the replay found, it catches all 27.

Enum values are available too, but in two shapes. Measured: 49 parameters carry an inline `enum` (object-changes `action`, device `face`, `airflow`), and 870 array-typed choice filters (`status` and its relatives) carry only an `x-spec-enum-id`; resolving those ids through `components.schemas` yields 82 enum tables and **919 enum-checked parameters with 0 unresolvable ids** ([proto_results.json cost](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/proto_results.json); [schema_coverage.md KQ6](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/schema_coverage.md)). This matters because off-the-shelf validators do not do the resolution: openapi-core, measured on this schema, accepts `?status=bogus` without error precisely because the parameter has no inline enum, spends 21.9 s validating the spec at construction, costs 75 ms per request, and never inspects undeclared query keys at all ([prior_art.md KQ5](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/prior_art.md)). The right tool is a twenty-line name-set index with enum resolution, which is what pynetbox ships as `strict_filters=True` since v7.6.0 (January 2026): `allowed_parameters = [p["name"] ...]` from `paths[...]["get"]["parameters"]`, `cf_*` skipped after issue #701, no type checks, no suggestions ([pynetbox endpoint.py](https://github.com/netbox-community/pynetbox/blob/master/pynetbox/core/endpoint.py); [pynetbox#695](https://github.com/netbox-community/pynetbox/issues/695); [pynetbox#701](https://github.com/netbox-community/pynetbox/issues/701)). The NetBox community client already made this bet.

What the schema cannot carry is the value layer, and the measured list is specific. `nullable: true` appears on 128 bare `*_id` parameters but measured live at least six "non-nullable" ids honour `null` (`rack_id=null` → 9, `location_id=null` → 70, `primary_ip4_id=null` → 97), and the slug form `tenant=null` works though unmarked, so nullability must not be enforced from the schema. 109 `*_id` parameters are typed `array<string>` because tree-node filters fall through drf-spectacular's "Defaulting to string" branch, so integer-ness must not be enforced either. `created__empty` is listed with a date-time type and answers 400 whatever you send. `has_primary_ip=1` and `=no` are dropped silently while `true`/`false` work, because django-filter's `BooleanWidget` accepts only those two strings. `vrf` on ip-addresses is a valid key whose description reads "VRF (RD)", so `vrf=hvl-guest` is a 400 the schema cannot predict; `site=DM-Scranton` likewise (description "Site name (slug)", the slug list is data). And `tenant__n=null` is a valid key that returns the complement, 126 devices with a tenant ([schema_coverage.md KQ1, KQ3, KQ7](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/schema_coverage.md)). Finally, three honoured parameter families are absent from the schema because they live outside the filterset: `fields` and `brief` (read directly from `query_params` in the viewset) and every `cf_<name>` filter (added per instance in `NetBoxModelFilterSet.__init__`). None of the 1,237 recorded calls used any of them inside `filters`, so their false-positive risk is reasoned rather than measured, but an exempt list closes it ([prototype_replay.md KQ1](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/prototype_replay.md)).

## Findings that need fixing whatever you decide

The investigation surfaced several defects that are independent of the schema decision. They are listed in order of damage.

**JSON `null` never reaches NetBox.** Measured through the real MCP tool in this session: `netbox_get_objects("dcim.device", {"tenant_id": null})` returns `count: 141` with Halvorsen and Dunder-Mifflin devices in the first page; `{"tenant_id": "null"}` returns 15 with `tenant: null`. The server calls `self.session.get(url, params=params)` with no `None` handling, and `requests` drops parameters whose value is `None` ([netbox_client.py:220](/home/ola/dev/rnd/mcp/testmcp/netbox-mcp-server/src/netbox_mcp_server/netbox_client.py)). The recorded runs agree: the 2026-10-18 call `{"tenant_id": null}` recorded count 141, the 2026-10-19 `virtualization.virtualmachine {"tenant_id": null}` recorded 208, the unfiltered total. Null-valued filter keys per run were 4, 2, 13 and 16, so the sentence in the 2026-10-18 doc counting thirteen correct null-form uses is wrong as a statement about what NetBox received; the doc's own curl verification sent the string `null` on the wire ([prototype_replay.md KQ3](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/prototype_replay.md); [2026-10-18 doc](/home/ola/dev/netboxdev/ollamaDeepAgents/docs/development/2026-10-18_filter-naming-after-in.md)). The fix is a one-line wire rule, `None -> "null"` for every filter value, in the wrapper or the MCP server; neither a schema key check nor the current hand rules can see it because the key is valid.

**`__regex`/`__iregex` are whitelisted but silently ignored on 4.3.3.** Measured live, `name__regex`, `name__iregex` and `serial__regex` all return 141 of 141; `name__isw=dmi01-akron` returns 3. The lookup exists from v4.3.5 (#19903). The project's `VALID_SUFFIXES` and upstream netbox-mcp-server's `valid_suffixes` both list them ([schema_coverage.md KQ1](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/schema_coverage.md); [upstream server.py](https://github.com/netboxlabs/netbox-mcp-server/blob/main/src/netbox_mcp_server/server.py)).

**`ordering` is wrongly whitelisted in the GraphQL pre-check**, and the pre-check's "`*_id` takes no lookup object" rule has a schema-proven false-positive class: measured, **53 input fields named `id`/`*_id` are not `ID` scalars** (`TenantFilter.group_id: TreeNodeFilter`, `ObjectChangeFilter.request_id: StrFilterLookup`, `L2VPNTerminationFilter.assigned_object_id: IntegerLookup`), on which a valid lookup object would be rejected locally ([gql_probe2.out](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/gql_probe2.out)). Whether the model ever uses those keys was not checked in the traces; the frequency is unknown, the defect is not.

The doc does not record the value it used, so the discrepancy cannot be resolved from the evidence, but the classification in the doc and in the `_IPADDRESS_PREFIX_ONLY_KEYS` comment should say "ignored" ([schema_coverage.md KQ1 gaps](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/schema_coverage.md)).

**The benchmark scoring has a blind spot.** The 31 wrong-name uses returned HTTP 200 and recorded outcome `ok`; nothing in the v5 wasted-call categories counts a call that silently returns the whole table. Inferred: any future category list should include "silently unfiltered" as its own class, detectable post hoc by comparing the returned count with the endpoint's unfiltered count.

**`graphql-core.validate` reproduces NetBox's messages exactly.** Measured over 25 reconstructed cases, every grammar and name error (`Unknown argument 'filter' ... Did you mean 'filters'?`, `Field 'icontains' is not defined by type 'StrFilterLookup'`, `Cannot query field 'virtualmachine_count' on type 'TenantType'`, `Variable '$id' of type 'Int!' used in position expecting type 'ID'`) came back byte-identical from local `validate` and from NetBox, and a five-error document produced the same five messages in the same order. ## Recommended design: four REST layers and a validate-based GraphQL pre-check

The design keeps the generic `filters: dict` tool shape and the existing `FilterValidator` entry point, and inserts schema-driven layers in front of the hand rules. Each layer is advisory-safe: it either rejects with a message the model can act on or passes the call through.

**Layer 0, wire normalisation (hand-written, runs first).** Map `None` to the string `"null"` for every filter value; leave lists alone (the MCP server already repeats the parameter, which is the schema's declared `explode: true, style: form` multi-value form; the comma form is a measured 400). Coerce Python booleans to `"true"`/`"false"`, since `BooleanWidget` accepts nothing else. This layer alone fixes the 29 unfiltered null calls in the two latest runs.

**Layer 1, key existence (schema-driven).** Resolve `object_type` to its endpoint through `NETBOX_OBJECT_TYPES` (all 126 entries resolve to a schema path), look the key up in the endpoint's parameter-name set, and reject with a message when absent. Exempt by rule: `cf_*` (as pynetbox does), `fields`, `brief`, `export`, `format`, and the MCP-level `limit`/`offset`/`ordering`/`q` if a model ever puts them inside `filters`. Fail open: if no index is available, skip this layer, log once, and let the hand rules run. A stale index is still correct for every one of the 27 keys above because none depends on instance data (inferred).

**Layer 2, enum membership (schema-driven).** For parameters with an inline `enum` or a resolved `x-spec-enum-id`, reject values outside the list and quote the list; the `action` description text ("* `create` - Created ...") is a ready-made message. This generalises the 10-19 `CHANGELOG_ACTION_FIX` to `status`, `face`, `airflow`, ip-address `role` and about 900 others. Keep it case-sensitive, matching NetBox (measured: `status=bogus` is a 400). Unmeasured: no recorded call carried a wrong `status`, so a case-insensitive acceptance by NetBox that the enum check would wrongly reject is a theoretical gap worth one live probe before enabling.

**Layer 3, value semantics and suggestions (hand-written, retained).** Keep exactly the rules the schema cannot express: `<relation>__n` with `null` or `true` (the complement trap); `<relation>__empty`/`__null`/`__isnull` → `<relation>_id="null"`; `vrf=<name>` → `vrf_id` or the RD; `created__empty`/`last_updated__empty` (listed but 400); the slug hint when a 400 names a parameter whose description ends in "(slug)"; and the `parent` hint for ip-address containment. Do not enforce `nullable`, `items.type` or `format` from the schema. For suggestions, run in this order: the existing `suggest_alternative` suffix rules; an alias table (`device_role`→`role`, `devicerole_id`/`device_role_id`→`role_id`, `circuit_type_id`/`cluster_type_id`→`type_id`, `vlan_group_id`→`group_id`, `cable_id`→`cable`, `assigned_object_*`→`object_*`, `contact_role_id`→`role_id`, `parent_prefix`→`parent`, `host_id`→`device_id`); then difflib top-3 with a guard that never emits a `__n` key for an input ending in `__in`, `__empty`, `__null` or `__isnull`; and when nothing matches, list the endpoint's `*_id` parameters, which is the only useful answer for "virtual disks have no tenant filter".

**Index lifecycle.** Vendor a pre-built index (about 1.1 MB JSON) stamped with `info.version`; at startup read `/api/status/` (one small GET) and refetch `/api/schema/?format=json` plus rebuild (about 0.6 s, 29 MB transient) only when `netbox-version` or the plugin list differs from the stamp; persist the rebuilt index beside the vendored one. Lazy per-endpoint loading is pointless because parsing the one document is the whole cost (measured). This is the same version-keyed strategy NetBox itself uses for its schema cache.

**GraphQL.** Replace the five grammar rules in `_validate_filter_grammar` (`filter:`, top-level `limit:`/`offset:`, unknown argument, id list, id lookup object) with `validate(schema, document, rules=[*specified_rules, NoNullIdFilterRule])` against the `GraphQLSchema` that `discover_schema` already builds and caches per endpoint. Keep three hand rules: the alias cap (runtime setting, not schema), `_validate_read_only` (`validate` passes `mutation { x }` against a schema with no mutation type), and the depth guard (NetBox's `GRAPHQL_MAX_QUERY_DEPTH` defaults to unlimited, so the local 12 is a cost guard). Add a thin enrichment layer that pattern-matches two graphql-core messages that carry no hint (`Unknown argument 'limit'`, `ID cannot represent a non-string and non-integer value`) and prepends the existing hand-written text, which names the fix. Key the schema cache on `/api/status/` version plus plugins, and drop the cache once when NetBox rejects a document that passed locally. Cost: 1.15 MB introspection (38 KB gzipped) fetched in 0.6 s, `build_client_schema` 188 ms cold, 2.4 MB resident, 1.4 ms per validation ([gql_introspect_probe.out](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/gql_introspect_probe.out)). The test suite already serves a real introspection through `httpx.MockTransport`, so the path is testable offline.

What stays hand-written, in one sentence: anything about what a value means (null sentinel, complement, RD, slug, boolean spelling, the broken `created__empty`), the exempt list for unlisted-but-honoured parameters, the alias table and complement guard for suggestions, and the three GraphQL runtime guards. What becomes schema-driven: which keys exist on which endpoint, which enum values exist, and the entire GraphQL grammar and name layer.

## Implementation plan with gates

The order puts the two bug fixes first because they change answers on the next benchmark run regardless of the schema work, and each later step has a replay gate that can be run offline against the recorded calls before any 90-question run is spent.

**Step 0, ship the null wire fix.** Add `None -> "null"` (and bool → `"true"`/`"false"`) in the wrapper's filter normalisation, or in `netbox_client.py` as a local patch alongside the two 2026-10-19 patches. Gate: a live MCP call `{"tenant_id": null}` on `dcim.device` returns 15, and a unit test asserts the wire parameter is the string `null`. Correct the "thirteen correct null-form uses" sentence in the 2026-10-18 doc and note the `without` reclassification.

**Step 1, correct the whitelists.** Remove `regex`/`iregex` from `VALID_SUFFIXES` (or gate them on `netbox-version >= 4.3.5`), remove `ordering` from `_LIST_FIELD_ARGS`, and restrict the GraphQL `*_id` lookup-object rule to fields whose introspected type is `ID` (or delete it in step 5). Gate: existing tests pass; a test asserts `name__regex` is rejected with a hint to `__ic`/`__isw` on 4.3.3.

**Step 2, build the index tool.** A script that fetches `/api/schema/?format=json`, builds `{endpoint: {name: {kind, enum}}}` with `x-spec-enum-id` resolution, stamps `info.version`, and writes the vendored JSON; the prototype's index build in `proto_replay.py` is the reference implementation. Gate: the index reports 145 list endpoints, 11,520 parameters and 919 enum parameters for 4.3.3; 126 of 126 `NETBOX_OBJECT_TYPES` resolve; load time under 50 ms.

**Step 3, layers 1 and 2 in `FilterValidator`, fail-open.** Insert ahead of the suffix rules with the exempt list. Gate: a replay over `proto_results.json` (1,237 calls) reproduces exactly 54 key rejections and 6 enum rejections with 0 rejections on any call the live checks marked honoured; the 3 hand-only catches still fire; the validator makes no HTTP call per request.

**Step 4, suggestion layer.** Alias table, complement guard, difflib fallback, `*_id` listing. Gate: 20 of 27 replay keys receive the right correction; no suggestion for a `__in`/`__empty`/`__null`/`__isnull` input ever contains `__n`.

**Step 5, GraphQL `validate`.** Wire the cached schema into `execute_graphql`, retain the three guards, add `NoNullIdFilterRule` and the two-message enrichment. Gate: the 25 probe cases produce the same messages as `gql_introspect_probe.out`; the alias, mutation and null cases are still rejected; all tests run offline through `MockTransport`.

**Step 6, one v5 benchmark run with everything on.** Compare against 2026-10-19. Gate for keeping the layers: silently-unfiltered calls (returned count equals the endpoint total while a filter was supplied) drop to zero; no new wasted-call category appears; the "devices with no tenant" and relation-name questions score correctly; total model turns do not rise by more than the number of rejections. This is the only step whose outcome is a projection rather than a measurement: the replay guarantees the catches, not the model's recovery in one turn, which was explicitly out of scope ([prototype_replay.md KQ5 gaps](/home/ola/dev/netboxdev/ollamaDeepAgents/tmp/research/research_notes/OpenAPI%20schema%20driven%20filter%20validation/prototype_replay.md)).

**Step 7, staleness and upstream.** Add the `/api/status/`-keyed refresh and a test that simulates a version change; file the `None` drop and the `action` docstring as netbox-mcp-server issues, citing pynetbox `strict_filters` if offering the key check upstream. Optional, later: a result-size heuristic (filtered count equals unfiltered total with a non-exempt filter present) as a post-hoc detector for `cf_` typos and anything else the schema cannot list, at the cost of one extra page.

## Conclusion

The three days of hand-written rules were not wasted; they encode exactly the value semantics the schema cannot carry, and the replay shows they catch three calls the schema misses. What they could never do is know that `dcim/devices` has a `role_id` but no `device_role_id`, and that single fact family produced more wrong answers in the two most recent runs than every suffix mistake combined. The schema decision is therefore less a replacement than a change of authority for one question, "does this name exist here", from a list someone remembers to a document the running instance publishes, with pynetbox as the precedent and the version-keyed cache as the maintenance story.

The more consequential discovery is that the benchmark's own ground truth was partly wrong: the null-form calls it counted as correct were unfiltered, the `regex` suffix it accepted was ignored, and the wrong-name calls it never counted were the largest silent category. A validator that rejects loudly is valuable precisely because a 200 with the whole table is the one failure the model, the harness and the analyst all read as success; the post-hoc "returned count equals endpoint total" check belongs in the scoring pipeline whether or not the schema layers ship.
